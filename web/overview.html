Architecture

Four source lanes feed one triage queue. Native APIs handle Hacker News and Stack Overflow, while Grok covers Reddit, X, and competitor mentions that need broader discovery and summarization.

Native intake

Algolia pulls Hacker News keyword hits and the Stack Exchange API pulls Stack Overflow tag and intitle matches with no LLM needed for initial retrieval.

Grok discovery

Separate Grok calls handle Reddit/X pain discovery and competitor mentions for Reducto, Unstructured, UiPath, and LlamaIndex. Native HN/SO candidates also pass through a Grok classifier for summary, reply angle, and categories. Both passes are steered by an ADE focus block that prioritizes visually-rich, structurally complex documents.

Queue storage

Qualified posts land in pain_posts with status, categories[], opportunity, and optional competitors[]. Duplicate URLs are merged rather than reinserted.

Human triage + cleanup

The frontend lets a human reply or delete. Untouched new posts older than 4 days are auto-archived nightly, then rolled into reports and the daily summary email.

Document targets

The ADE focus block injected into every discovery and classifier prompt steers Grok toward the document types where LandingAI ADE has a real differentiator vs commodity OCR — visually-rich, structurally complex, often domain-specific. Generic plain-text OCR posts are explicitly de-prioritized.

Operating Model

The core behavior is intentionally narrow: find real pain, frame it cleanly, and let a human respond. Everything else in the system exists to support that loop without drifting into classic lead-gen behavior.

boundary

Not lead-gen

No Apollo sequence enrollment, no person-to-company resolution, and no writes into pg_leads. This project ends at the moment a human sees a strong post and decides to reply.

quality gate

Keep only useful pain

HN and SO are filtered through a classifier that defaults to keep unless content is obvious vendor marketing or off-topic. Grok returns fewer posts rather than padding with weak signal.

throughput

Fast cadence, small queue

Typical cycles insert roughly 5–15 posts before dedup and around 5–10 after dedup. The point is not volume. It is fresh, reply-worthy context.

APIs

Six services, zero custom infrastructure. Native structured APIs handle HN and SO at no LLM cost. Grok covers the open web. Supabase holds state. Brevo delivers alerts. nginx serves the frontend.

Algolia

hacker news search
hn discovery

Powers Hacker News full-text search via the Algolia HN API. Runs 20 tuned keyword queries per cycle with no API key required. Candidate posts then pass through the Grok classifier for summary and reply angle.

stack overflow search
so discovery

Queries Stack Overflow via the Stack Exchange API using 9 tag filters and 32 intitle text queries per cycle — 41 calls total, well under the registered key's 10,000/day quota. High-precision pre-filter means fewer false positives than open-text search.

xAI — discovery + classifier
reddit / x / classify

Three separate passes per cycle: Reddit + X pain discovery, competitor mention monitoring (Reducto, Unstructured, UiPath, LlamaIndex), and HN/SO classification into {summary, opportunity, categories[]}. Runs on grok-4.3. Source-level failures are non-fatal and alert immediately via Brevo.

Performance

The system is optimized for low-cost, high-signal refresh rather than heavy enrichment. Native APIs do the structured work, Grok handles the fuzzy work, and the queue stays small enough for a human to actually use.

cadence

3× daily, Mon–Sat

Discovery runs at 9:02 AM, 1 PM, and 6 PM ET, Monday through Saturday — spread across the workday so the triage queue refreshes without piling up unread posts between sessions.

typical cycle

5–10 net posts

After source fetch, classification, dedup, and DB overlap checks, a normal production cycle lands a handful of usable cards rather than a flood of noise.

retention

4-day archive window

New posts that nobody touched are flipped to archived at 11 PM ET, which keeps the queue focused and makes reports easier to interpret.

frontend contract

Reload-based freshness

The queue loads on page visit and refreshes on browser reload. There is no auto-polling and no in-app refresh button because the cron cadence already does the heavy lifting.

Security model

Three concentric layers of defense in depth. Punching through the perimeter still requires a valid secret. Stealing the secret still can’t exceed rate caps baked into the database.

Layer 1

Perimeter

cloudflare · nginx

Cloudflare proxies all traffic — providing DDoS mitigation and TLS termination before requests reach the origin. nginx enforces HTTP basic auth on /config.js, the only file that holds Supabase keys and the RPC secret. Multi-tenant deployments use per-user htpasswd entries so each team member gets their own credentials; nginx validates them separately with no shared password. Security headers prevent clickjacking, MIME-type sniffing, and unintended referrer leakage across the entire site. HTML and config files are served with Cache-Control: no-store.

Cloudflare proxy + TLS htpasswd — per-user credentials config.js auth-gated X-Frame-Options: SAMEORIGIN X-Content-Type-Options: nosniff Referrer-Policy: strict-origin Cache-Control: no-store
Layer 2

Backend access controls

supabase RLS · secret RPCs

pain_posts allows anon SELECT — reads are safe to expose, writes are not. pain_miner_secrets and pain_miner_errors have RLS enabled with zero policies, so the anon role is fully blocked on both read and write. All mutations route through two secret-gated RPCs — set_pain_post_status and log_painminer_error — that validate a shared secret server-side before executing. Server scripts hold the service-role key and it never leaves the droplet. set_pain_post_status accepts an optional p_user parameter: the authenticated username parsed from the client’s htpasswd session, written to actioned_by + actioned_at on every Reply / Delete / Archive for a full audit trail.

RLS — anon select-only on pain_posts RLS — anon fully blocked on secrets + errors set_pain_post_status RPC (+ p_user audit) log_painminer_error RPC actioned_by + actioned_at audit columns service-role key server-only
Layer 3

Input hardening + rate limits

url validation · db rate cap

Every ingest URL is validated at write time — only http:// and https:// schemes accepted; javascript: and data: URIs are rejected before touching the database. The frontend safeHref() re-validates all URLs before rendering any anchor as a second line of defense. The error-logging RPC enforces a hard 20-events-per-fingerprint-per-hour cap inside the database — it cannot be bypassed from the frontend. Fingerprints are truncated to 64 chars before the rate-limit COUNT to close the suffix-variation bypass.

http/https-only URL ingest javascript: + data: blocked safeHref() frontend re-check 20 / fp / hr RPC rate cap fingerprint truncation at 64 chars

Multi-tenant access

per-user htpasswd

Each team member gets their own htpasswd credential — no shared password. nginx validates them independently. The authenticated username is parsed from the session token on the client and passed to set_pain_post_status as p_user, so every Reply, Delete, and Archive action is recorded against the specific user who took it in pain_posts.actioned_by + actioned_at. To add a user: sudo htpasswd /etc/nginx/painminer.htpasswd <username>.

Frontend error digest

15 min cadence

error-shim.js captures window.onerror, unhandledrejection, and explicit app errors, fingerprints them, and batches them into a Brevo email digest every 15 minutes so frontend regressions surface without manual console inspection.

Ops visibility

daily + real-time

Brevo delivers source-level Grok failure alerts in real time, daily queue summaries at 11:30 PM ET, and frontend error digests grouped by fingerprint — so any degraded state is visible the same day it happens.
